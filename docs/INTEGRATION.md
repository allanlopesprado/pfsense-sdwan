# pfSense forwarding and IPsec integration

The package recommends one member per policy using dpinger, the pfSense gateway monitor. On stock CE, the recommendation is informational and native configuration governs forwarding. The forwarding engine recognizes existing bindings on steering ABI 1 or 2. New approvals and changes require the current adapter and a verified PF load at boot. Verify each flow in both directions to establish its actual path. Acceptance on pfSense CE 2.9.1 and 2.9.2 requires the traffic tests below, including when the peer runs FortiOS.

## Finding SD-WAN in pfSense

From 0.4.30, **Status → SD-WAN** shows monitored gateways and policy recommendations. **Diagnostics → SD-WAN** opens policy evaluation, service results, and relevant native tools. **Services → SD-WAN** remains the package entry for configuration, forwarding approval, and updates. The tab bar and bookmarked URLs work from either menu.

Use **Status → Services** to manage the observer and **Status → System Logs** to see its log entries. The new Status and Diagnostics entries depend on the existing SD-WAN view privilege. Native tools remain subject to their own privileges.

## What the package accesses

| Component | Package operation |
|---|---|
| Gateways and monitoring | Reads saved gateway and interface entries and queries the dpinger status socket for configured members. The administrator's choice of target determines what the measurement covers. |
| Configuration | The editor saves members, SLAs, and policies under `installedpackages/sdwan` through the native configuration system. The experimental core records rule bindings under `gateways/sdwan_bindings`. Installation and removal use the pfSense package registry. |
| Measurement and decision | The daemon publishes results to `/var/run/sdwan-observer.json`. The engine evaluates samples against the SLA. RTT and RTT standard deviation come from gateway probes. |
| Forwarding and VPN | In observation mode, the package publishes a recommendation. With the experimental API and bound rules, it requests a native filter reload to apply its choice to new connections. The core controls existing states. The package selects the gateway on bound rules. IPsec, NAT, CARP, FRR, and the default route are native responsibilities. |

## Topology matrix

| Topology | What the readings show | Firewall checks |
|---|---|---|
| One WAN | The package can monitor the link. A failure leaves a single-path policy without an alternative. | Compare a next-hop response with a connection to the actual service. A modem can respond during an ISP outage. |
| Two WANs without IPsec | Each gateway can have a reading. Both WANs can provide direct Internet access. | Check client egress, source translation, the address seen at the destination, and the return path on each WAN. Test NAT port forwards separately. |
| Two VTIs on distinct WANs | The package can compare assigned tunnel gateways that are present in the inventory and monitored. | Bind each probe to its path. Verify IKE and CHILD_SA, the WAN route to the public peer, the remote route through the VTI, and the remote client's response. |
| Two VTIs on one WAN | Both can have valid RTT measurements and still fail together. | Determine which Phase 1, circuit, and physical link supports each VTI. Distinguish a tunnel outage from failure of the shared WAN. |
| Direct WAN and VTI | Each sample describes its own target. A public target can respond while the private network is unreachable. | Compare paths that meet the same destination and encryption requirements. For protected private prefixes, verify that loss of all tunnels prevents cleartext egress. |
| Policy-based IPsec, including mobile | A peer's public IP can respond while the tunnel is down. Traffic selectors alone do not create a selectable VTI gateway. | Check Phase 2 selectors, association counters, and the remote service. In mixed deployments, preserve processing for policy-based tunnels. |
| HA with CARP | Each node observes its local paths. A VIP's MASTER status identifies its owner. | Select the terminating WAN's CARP VIP in Phase 1. Assign VTIs in the same order on both nodes. Time renegotiation and the first application response after failover. |

## Settings that affect actual traffic

**Default routes and IPsec selectors.** In the system routing table, `0.0.0.0/0` is the IPv4 route used when no more specific one matches. In IPsec, a `0.0.0.0/0` selector describes the address range the peers agree to protect. Both are configured outside the package. For a full tunnel, verify the route to the peer's public IP, the internal destination route, and the return path. For two WANs with the same peer IP, capture the IKE egress path for each connection. The native generator decides whether to add a specific route, including the case of duplicate peers. Repeat with `::/0` for dual stack. [IKEv2 traffic selectors in RFC 7296 §2.9](https://www.rfc-editor.org/rfc/rfc7296.html#section-2.9) · [VTI and automatic default routes](https://docs.netgate.com/pfsense/en/latest/vpn/ipsec/routed-vti.html) · [Native peer route code](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/etc/inc/ipsec.inc#L2045-L2096)

**Filtering, NAT, and states.** In the default IPsec mode, VTI traffic passes through the IPsec tab and can appear on `ipsecX` and `enc0`. This affects interface-bound states. For NAT and `reply-to` on assigned VTIs, Netgate documents filtering on assigned interfaces. This global setting blocks tunnel-mode traffic and is incompatible with mobile IPsec. In a mixed deployment, review the documented alternative of floating states on specific VTI rules. For WAN NAT, verify that the translated source matches the chosen egress and, in HA, the intended VIP. [VTI filtering](https://docs.netgate.com/pfsense/en/latest/config/advanced-firewall-nat.html#ipsec-vti-filtering) · [Multi-WAN NAT](https://docs.netgate.com/pfsense/en/latest/multiwan/nat.html)

**Return path and connection origin.** In PF, `route-to` affects packets in the direction of the rule and `reply-to` affects replies for a stateful connection. A LAN ingress rule with a gateway can also match VPN destinations if the exceptions are below it. Connections started by the firewall, such as DNS queries, follow route table and service binding settings. Test a connection from LAN, an external connection to a published service, and a connection initiated by the firewall. [Routing options in pf.conf(5)](https://man.freebsd.org/cgi/man.cgi?query=pf.conf&sektion=5) · [Rule order and unavailable gateways](https://docs.netgate.com/pfsense/en/latest/multiwan/policy-route.html) · [Local services and multi-WAN](https://docs.netgate.com/pfsense/en/latest/multiwan/considerations.html)

## Native gateway groups when all paths fail

A LAN ingress rule can use a native gateway group. pfSense resolves the members and generates `route-to` for the first usable tier. Healthy members in the same tier can share connections. Before using a dedicated group, identify references in rules, IPv4 and IPv6 defaults, Phase 1, and services such as OpenVPN and Dynamic DNS. Changing tiers can affect any consumer of that group name. [Gateway groups](https://docs.netgate.com/pfsense/en/latest/routing/gateway-groups.html) · [Native group application](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/usr/local/www/system_gateway_groups.php#L43-L70)

For VPN-only prefixes, the last eligible path matters. With **System → Advanced → Miscellaneous → Do not create rules when gateway is down** cleared, the generator can retain the pass rule and use the ordinary routing table. With it enabled, the filter can omit that rule and continue to the next one. Netgate's example pairs the enabled setting with an immediately following native block or reject that covers protected traffic and still applies when the package is stopped or removed. Verify effective ordering, floating and interface group rules, exceptions, and existing sessions. Assess how the global setting affects other firewall rules. [Enforcing gateway use](https://docs.netgate.com/pfsense/en/latest/multiwan/policy-route.html#enforcing-gateway-use) · [Gateway macro generation](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/etc/inc/filter.inc#L1732-L1857) · [Rule generation](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/etc/inc/filter.inc#L4467-L4484)

The core provides a package rule generation hook. The generator can skip it while installation or upgrade holds the package manager lock, or when the package fragment fails syntax validation. Verify the persistent PF block after package removal as part of the cleartext containment test. Acceptance during a configuration change depends on the loaded ruleset and state policy, so verify actual packet delivery as well as static configuration. [Hook and syntax validation](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/etc/inc/filter.inc#L6098-L6162)

pfSense omits policy-based IPsec selectors of `0.0.0.0/0` and `::/0` from its automatic VPN routing exceptions. If an enabled full tunnel covers the source of a direct WAN binding, SD-WAN rejects the binding or withdraws its forwarding target on the next filter reload. Use explicit native VPN rules for protected sources. WAN policies for separate source prefixes remain eligible.

Administrators with native routing and firewall edit permissions can tune a bound SLA, member cost, or selection strategy from the normal editors. The package writes the new settings and the approved binding revision together after checking the same native rule scope and gateways. Forwarding shows the selected gateway and verifies the compiled PF rules for new connections. The observer checks the loaded rules once the reload queue has had 30 seconds to apply its request. It retries when an active ruleset differs from the SD-WAN decision and records the mismatch under System Logs. Changes in the desired path continue to request a reload immediately. If PF is disabled or its rules are unavailable, the package cannot verify the decision. Loaded PF rules can persist while the observer and filter reload service are both unavailable.

**Active DNS, HTTPS, and TCP checks.** Each member can specify a primary and a secondary service target. Add a native host route for each distinct target IP via that member's gateway. Checks bind to the current interface source and verify the host route before and after the request. For a pfSense-managed PPP link, the check also accepts a direct `/32` or `/128` route to the target on the expected interface when the kernel reports that interface as up and point-to-point. DNS requires a complete A answer for the queried name or its CNAME chain. HTTPS requires a valid certificate and a 2xx response. TCP verifies that the server accepted the connection. An optional RTT standard deviation limit uses the value measured by dpinger. Review the individual results in Diagnostics. [FortiGate link health monitoring](https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/580649/link-health-monitor) · [FreeBSD route(8)](https://man.freebsd.org/cgi/man.cgi?query=route&sektion=8)

**Policy eligibility.** Leave both slots at **Member default** to accept any passing configured check. With explicit policy settings, an unselected slot is ignored. When any check is required, every required check must pass. Without required checks, one selected optional check must pass. Selecting **Ignore** for both slots makes eligibility depend on the gateway SLA. Override either slot for an individual candidate if that path reaches the service through a different slot. For example, an ERP policy can require the ERP probe on each WAN while a backup policy reuses those WANs and requires its own probe. Diagnostics identifies required checks, verified failures, and missing measurements. To downgrade to a build that predates these fields, first clear both policy settings and all member overrides, or restore a compatible configuration backup.

Diagnostics identifies an unavailable check, an unverified route, a timeout, and a verified service failure separately. A completed response counts only while the host route and source still identify the same path. Each routing table holds one selected route to a given host. Two targets can identify the same service by using distinct host addresses, the same HTTPS name, and the same application response. Confirm the source at the server and capture each WAN while keeping the default route. [Native monitor routes](https://docs.netgate.com/pfsense/en/latest/routing/gateway-configure.html) · [Traffic originated by the firewall](https://docs.netgate.com/pfsense/en/latest/multiwan/considerations.html)

**Application readiness over HTTPS.** An endpoint can return HTTP 200 while its application is unavailable. Append an expected token to the check, for example `https://erp.example/ready 192.0.2.168 expect=erp-ready`. The response must have a valid certificate, a 2xx status and the exact token in its body, with an optional LF or CRLF. Tokens use 1–64 ASCII letters, digits or `._:-`. Diagnostics reports a marker mismatch separately. The check buffers at most the token length plus two bytes, and response contents stay out of System Logs. Checks without a marker keep their existing behavior. [FortiOS health check options](https://docs.fortinet.com/document/fortigate/7.6.5/cli-reference/838040159/config-system-sdwan)

**DNS records by address family.** The DNS check queries `A` by default. Set `type=AAAA` for an IPv6-only service, for example `dns://erp.example 192.0.2.168 type=AAAA`. The DNS server's IP selects the transport family and its gateway must match. The answer must contain the requested record type for the name or for its CNAME target. [RFC 3596](https://www.rfc-editor.org/rfc/rfc3596.html#section-2.3)

**Interface traffic in Diagnostics.** Select a policy and click **Measure** to read receive and transmit rates on its resolved interfaces. The rate is the change in byte counters over a short interval, covering all traffic on each interface. The feature is read-only and independent of health checks and forwarding. The current interval is discarded after a counter reset or policy change. [Netgate interface monitoring](https://docs.netgate.com/pfsense/en/latest/monitoring/graphs/bandwidth-usage.html)

**Shared destination with separate FreeBSD routing tables.** Provision a nonzero FIB for each WAN and install the gateway and probe host routes in those tables. In Members, enter `fib=1 tcp://192.0.2.168:7` on the first member and `fib=2 tcp://192.0.2.168:7` on the second. The prefix also works with DNS and HTTPS checks. Entries without a prefix keep the original routing table. The package rejects two checks for the same address within one table. It runs each prefixed check in a bounded process and verifies the expected interface and next hop in that FIB before and after the check. [FreeBSD setfib(2)](https://man.freebsd.org/cgi/man.cgi?query=setfib&sektion=2) · [FreeBSD route(8)](https://man.freebsd.org/cgi/man.cgi?query=route&sektion=8)

In the Members editor, use **Review probe routes** to check a draft without saving it. The review reads the current FIB count and checks the target host route for the member's gateway. It reports the expected interface, source address and next hop when available. For a duplicate target in one table, it suggests a different FIB number available for that target in the SD-WAN configuration. Confirm that table is dedicated to this WAN before provisioning its host routes. Recheck both members after applying the routes. Use Diagnostics after saving to verify the service responses.

Use `sysctl -n net.fibs` to confirm the kernel provides both tables. Verify each `route -n get -host 192.0.2.168 -fib N` shows the intended WAN and next hop. These tables belong to the administrator. Restore their host routes through the site's boot and WAN-renewal procedures, then verify both checks in Diagnostics before binding a policy. The package does not provision routing tables or write routes. Removing or crossing the routes turns the corresponding checks into unverified paths. The appliance acceptance uses separate WAN counters to verify the shared target and checks that crossed table assignments generate no probe packets.

**Degradation and recovery.** The default removes a path on the first observation outside the SLA and blocks new bound traffic when no path qualifies. A policy can set **WAN degradation samples** to 2–6 to keep an already applied, approved path until that many consecutive samples exceed a measured WAN quality limit. A matching loaded PF rule is required for the hold. A down gateway, missing measurement, or service check failure removes the path immediately. **Path recovery hold** controls how many seconds a healthy challenger must remain preferred before replacing a healthy current path with lowest-cost or lowest-RTT selection. The default is 30 seconds. A positive hold also delays the readmission of each recovered member to a weighted pool while another healthy member remains in the pool. Each eligible path has its own timer. If the pool loses every healthy member, eligible paths join immediately. Weighted balancing adds eligible paths immediately when the hold is omitted or set to zero.

**Weighted balancing.** The strategy spreads new connections across SLA-eligible gateways using their native gateway weights. The dedicated group must put every member in the same tier and the firewall must run steering ABI 2. The Forwarding preview identifies the required native rule pairs and checks active PF hops after loading. Each existing connection retains its established PF state. After the filter applies a healthy alternative, an authorized operator can reconnect sessions from a failed path. This action identifies each state by its originating rule tracker, next hop and exact state ID. [FortiGate SLA strategy](https://docs.fortinet.com/document/fortigate/7.6.4/administration-guide/342836/lowest-cost-sla-strategy)

**Automatic session reconnection.** In Policies, **Sessions on a failed path** defaults to keeping sessions. Administrators with firewall edit, gateway group edit, and state management privileges can opt into one batch of up to eight state removals for a verified gateway outage or a failed required service check on a direct WAN. This applies to lowest cost and lowest RTT policies after PF confirms an eligible replacement. The observer requires a recent PF readback of the former path, the same binding, and the exact old interface and next hop. An observer restart, confirmed total outage, expired prior readback, or changed next hop can prevent automatic recovery. Restrictions in native gateway and group state settings still apply. The observer skips a busy filter and leaves remaining or unverified states for manual review. Before manually downgrading to a package without this field, switch it back to **Keep existing sessions**. [Netgate gateway group state settings](https://docs.netgate.com/pfsense/en/latest/routing/gateway-groups.html)

**Experimental core bindings.** Reboot after installing or replacing the matching overlay before saving a new forwarding approval. The adapter checks for a native PF load during boot with the installed overlay. The group must exactly match policy members and contain at least two monitored gateways with alarm actions enabled, one IP family, and identifiable transports that do not share ports. Preflight checks VLAN, QinQ, LAGG, bridge, and PPP dependencies configured in pfSense. Use either all direct WANs or all VTIs. The VTI pilot requires filtering on assigned interfaces, an identifiable Phase 1 transport, and no active policy-based or mobile IPsec that conflicts with that mode. Distinct interface names can still share a physical circuit. Demonstrate physical independence and reachability to the same destination in the lab.

**Upgrading an existing VTI binding.** The approval now includes the enabled Phase 2 endpoints for the assigned VTI and the IP addresses and CARP VHIDs in its Phase 1 VIP chain. VTI bindings saved under the previous revision format require a new approval. With a stale approval, the next filter generation blocks new protected flows for that binding. During a maintenance window, verify the native gateway group and its block rules before removing the old binding. Then preview and bind the policy in **Services → SD-WAN → Forwarding** and verify it with a new connection. Ordinary IPsec rekeys and changes in CARP ownership preserve the approval. [Routed IPsec](https://docs.netgate.com/pfsense/en/latest/vpn/ipsec/routed-vti.html) · [CARP and stacked IP aliases](https://docs.netgate.com/pfsense/en/latest/highavailability/reduce-heartbeat-traffic.html)

Each bound ingress rule needs a unique native tracker and a persistent block or reject immediately after it. Both must use the same internal interface and equivalent match criteria. The pilot accepts literal addresses and prefixes, the ingress subnet, and numeric ports. At least one endpoint must be scoped. A direct WAN policy can use destination `0.0.0.0/0` or `::/0` with a specific source. Place explicit local, static-route, and VPN exceptions above the broad rule so they remain accessible when paths fail. For a VTI policy, provide the protected prefix or destination address. The experimental adapter excludes schedules, packet tagging, associated NAT, and floating rules. A binding records the revision of the policy, rule predicates, and paths. Review the binding after relevant changes.

**Native host aliases for direct WAN rules.** Use the same native Host alias as the destination of both rules. Use explicit IP addresses or FQDNs in the alias. pfSense resolves these names and maintains the PF table, and Forwarding confirms that the active rules reference that exact table. Changing the configured alias definition requires a new approval. Live address updates from native DNS resolution use the existing approval. Check the addresses in **Diagnostics → Tables** and test a new connection, particularly when clients and the firewall receive different DNS answers. [Netgate alias resolution](https://docs.netgate.com/pfsense/en/latest/firewall/aliases-features.html#hostnames-in-aliases)

**Policy event history.** Diagnostics shows the recent named decisions and PF confirmations from the active System Log to administrators with native log access. The history reflects retained events and their native timestamps.

The operator controls surrounding rules, NAT, states, routes, and native configuration. Deleting a group in pfSense can clear the gateway field on related rules. This can put a pass rule using the regular route ahead of the block. Test the actual loaded filter, persistent blocks, and continued identification of the rules by the core. Before accepting traffic that requires encryption, test removal, reordering, editing, stopping the package, and restoring native routing. [Native gateway group deletion](https://github.com/pfsense/pfsense/blob/9363ac5b8651a1c7a333180425ce7719070f95f9/src/usr/local/www/system_gateway_groups.php#L74-L94)

## Acceptance tests

1. Record versions, topology, probe targets, VTI-to-WAN mappings, IPv4 and IPv6 routes, PF and NAT rules, and IPsec associations. Keep a successful transaction as the baseline.
2. On the clone, repeat the same flows before and after saving a policy. Record egress and return interfaces, translation, and client results. For a VTI, capture the inner flow, destination response, and ESP or UDP/4500 on the WAN. Confirm arrival at the peer in addition to observing the outbound packet on the VTI before encryption. Include an HTTPS transfer or another payload sufficient to exercise MTU.
3. Separately take down only the target, only the tunnel, and only one WAN. Then test loss of both paths. Record the recommendation, actual path, established session recovery, and time to a successful new connection. Confirm by capture that a VPN-only destination remains protected without a usable tunnel.
4. In HA, repeat during active node failure and return. Record the MASTER for each VIP, time to the new CHILD_SA, and time to the first successful application reply. Recovery can depend on DPD, peer initiation, and native states.
5. Against FortiOS, record the version, proposals, identities, selectors, and routes at both ends. Test both directions, rekey, failure, and recovery. Acceptance requires application and return traffic observed in the same topology. [Lab procedure](LAB.md) · [Interface capture for outbound and return traffic](../tests/lab/observe-path.md)

### Isolated FreeBSD kernel tests

In a disposable FreeBSD VM with VNET, the CARP test verifies LAN and WAN VIP transfer and new TCP transactions using the WAN VIP as the NAT address. The pfsync-disabled control requires a new connection after failover. With pfsync on a dedicated link and floating states, the standby must receive the established TCP state with the same PF state ID and creator. The original connection must complete another transaction after both failover and failback. Testing with interface-bound states, configuration synchronization, and IPsec renegotiation requires the pfSense pair described below. [Project CARP test](../tests/lab/freebsd-carp.sh) · [pfSense state synchronization](https://docs.netgate.com/pfsense/en/latest/highavailability/pfsync.html)

A separate test routes through a VTI without an IPsec association in two jails, checking the missing-SA counter and packet delivery at the peer. Controls using the physical route demonstrate that the destination answers before and after the failure condition. [VTI without SA test](../tests/lab/freebsd-vti-no-sa.sh)

The validation matrix records vendor sources, test criteria, and required evidence. Interoperability and convergence times depend on the exact versions, topology, and observed transaction. [Validation matrix](VALIDATION.md)

## Check the IPsec endpoint on a CARP pair

In pfSense, check **VPN → IPsec → Tunnels → Phase 1 → Interface** for each HA peer. Select the terminating WAN's CARP VIP according to the approved topology. On FortiGate, verify that the remote address matches that VIP. A Phase 1 configured with an individual node's address can leave it as the only reachable endpoint. The package preview checks the VTI's transport. Verify the WAN VIP owner and that the peer negotiates with the VIP.

On a clone, before shutting down the MASTER, record the owners of the LAN and WAN VIPs, the local interface used by each Phase 1, and the last successful tunnel transaction. Repeat after VIP transfer and after the node returns. Observe the new CHILD_SA on the WAN VIP owner and a complete application round trip. Compare the time to VIP transfer, SA installation, and application recovery.
