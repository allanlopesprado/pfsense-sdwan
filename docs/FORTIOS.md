# FortiGate interoperability over two IPsec tunnels

The target scenario is a pfSense branch with two WANs, two route-based IPsec tunnels, and a FortiGate at the far end. Each firewall manages its own side. End-to-end acceptance with a FortiOS peer remains pending on pfSense CE 2.9.1 and 2.9.2. Repository tests exercise package, rule generation, and FreeBSD components. In the paired test, record the exact versions and application traffic in both directions. [Integration](INTEGRATION.md) · [Lab](LAB.md)

## Capabilities and limits

| Area | Project implementation | FortiGate or Junos reference |
|---|---|---|
| Measurement | dpinger reports RTT, RTT standard deviation, and gateway loss. SLAs use RTT and loss. Among eligible members, a policy prefers the lowest configured cost or lowest RTT. A single member supports SLA monitoring. | FortiOS also measures jitter, supports passive measurements, and makes decisions using its own rules. Junos RPM measures response time, variation, and loss. The three methods can produce different values on the same path. |
| Forwarding | Stock pfSense uses the recommendation for observation. With the experimental ABI 1 core, an explicit binding can select a gateway for new flows matching the identified rules. A binding requires a dedicated group, members of the same address family, and an adjacent block rule of equal scope. | The operator configures zones, routes, and SD-WAN rules on FortiGate. Each firewall selects its own member. |
| Two tunnels | Enabling a binding requires two VTI gateways with distinct, identifiable transport interfaces. Two children of one Phase 1 share IKE negotiation and transport dependencies. Different VLANs or virtual NICs can still use the same physical circuit. | FortiGate can group IPsec interfaces in an overlay zone. On Junos, routing selects a secure `st0.x` interface and security policies authorize the traffic. |
| Administration | The operator manages IKE, CARP, NAT, routes, and remote policies. | Centralized FortiManager management, dynamically formed ADVPN tunnels, and application selection are FortiOS capabilities separate from this package. |

## Where to use `0.0.0.0/0`

| Location | Effect and verification |
|---|---|
| CHILD_SA selectors | The reviewed pfSense VTI code adds broad IPv4 and IPv6 selectors. FortiGate permits broad local and remote selectors. Check the **negotiated** selectors in each CHILD_SA. The Phase 2 network fields in pfSense VTI mode define the tunnel's inner addresses. |
| LAN rule destination | Native pfSense rules can send a selected source to a tunnel even with destination `any`. Preserve local, management, and other VPN exceptions in the rule order. The experimental SD-WAN VTI binding requires a specific protected destination, even with a specific source. |
| Default route in the system table | Changes the overall IPv4 path, including local services according to their routes and bindings. The package rejects the system default gateway group for experimental binding. In a full-tunnel design, verify that public IKE addresses stay reachable over physical WANs during failure and reconvergence. Evaluate `::/0` separately. |

## Keep the return path on the same tunnel

1. **Confirm where the /0 is set.** A FortiGate Phase 2 selector of `0.0.0.0/0` permits those addresses inside the negotiated CHILD_SA. Verify selectors on both tunnels. A default route or catch-all SD-WAN rule can also send traffic into the tunnel. For a site-to-site VPN, route the actual protected prefixes and check whether FortiOS `add-route` has installed an unintended selector-derived route. If a site intentionally uses the other firewall for Internet egress, agree on the affected subnets, actual default route, egress NAT, and what happens when both tunnels fail. [FortiOS selector route option](https://docs.fortinet.com/document/fortigate/7.6.6/cli-reference/305883427/config-vpn-ipsec-phase1-interface) · [pfSense Phase 2 and VTI addresses](https://docs.netgate.com/pfsense/en/latest/vpn/ipsec/configure-p2.html)
2. **Keep the two underlays independent.** Use a separate IKEv2 Phase 1 and an assigned VTI for each WAN, with different inner point-to-point subnets and distinct monitoring destinations. Verify the actual egress of IKE/ESP or NAT-T for each WAN. Prefer distinct public peer endpoints when possible. pfSense's **Gateway Duplicates** setting disables automatic WAN-specific peer routes, so a common remote IP needs an explicit underlay design and captures on both paths. [pfSense IPsec and Multi-WAN](https://docs.netgate.com/pfsense/en/latest/multiwan/ipsec.html) · [Gateway Duplicates](https://docs.netgate.com/pfsense/en/latest/vpn/ipsec/configure-p1.html)
3. **Align A as primary and B as backup for new sessions on both peers.** Use native pfSense routing or a monitored VTI gateway group scoped to remote prefixes, and an equivalent FortiGate policy or routing preference with per-tunnel health checks. Avoid ECMP for this initial profile. With many prefixes, use FRR/BGP over the VTIs, with explicit prefix filters and preferences, as the shared routing policy. Keep a usable route to the source on the ingress overlay wherever FortiOS reverse-path checks require one. [pfSense dynamic routing over VTI](https://docs.netgate.com/pfsense/en/latest/vpn/ipsec/routed-vti.html) · [FortiOS reverse-path checks](https://docs.fortinet.com/document/fortigate/7.4.1/administration-guide/139692/routing-concepts)
4. **Keep replies on the ingress VTI.** In a VTI-compatible pfSense deployment, use the assigned-interface IPsec Filter Mode and a stateful pass rule on each VTI's own tab for the allowed remote and local prefixes. Check that each compiled rule has `reply-to` with its own VTI and peer next hop. Leave the global and per-rule **Disable Reply-To** options clear for those rules. The filter mode is global and blocks policy-based and mobile tunnel traffic. In mixed deployments, keep the compatible filter mode and use a coordinated routing design or a separate VTI firewall for this profile. Per-rule floating states can address `enc0` state matching but do not pin replies to a tunnel. [IPsec Filter Mode](https://docs.netgate.com/pfsense/en/latest/vpn/ipsec/advanced.html) · [pfSense state policy and reply-to](https://docs.netgate.com/pfsense/en/latest/config/advanced-firewall-nat.html)
5. **Check the FortiGate session in both directions.** For this symmetry profile, verify the FortiOS `auxiliary-session` setting because it can change how the reply path is chosen. Fortinet recommends disabling it in hub-and-spoke designs that expect replies on the original ingress interface. Keep state tracking and reverse-path checks in place. Verify recovery with a new connection and record separately whether an existing session survives. A pfSense SD-WAN decision controls the local egress only in the experimental core. On stock CE, our package supplies telemetry and recommendations while native routing and PF enforce the paths. [Fortinet return-path behavior](https://docs.fortinet.com/document/fortigate/7.6.6/administration-guide/14295/controlling-return-path-with-auxiliary-session)

The isolated Linux lab negotiated both selectors as `0.0.0.0/0` on two tunnels. Captures showed A/A, A/B, and B/B request/reply paths as the peers' route preferences changed. Removing B's SA stopped protected probes while the route still pointed to B. The probes recovered on A after both peers switched back. [Shared-selector lab evidence](https://github.com/allanlopesprado/pfsense-sdwan/actions/runs/44556848898/job/135675099615)

## Settings to agree on with the peer administrator

| Layer | Checks for each pfSense–FortiGate pair |
|---|---|
| IKE | Bind each Phase 1 to the corresponding WAN or WAN VIP for independent paths. Agree on IKE version, local and remote identities, PSK or certificate authentication, and compatible encryption, integrity, PRF, and DH proposals. Record DPD, timers, and rekey behavior. |
| ESP | Associate each Phase 2 with its Phase 1. Agree on ESP proposals, selectors, and PFS/DH group. Record lifetimes and verify CHILD_SA rekey while traffic flows. Use distinct inner address pairs and verify the neighbor on each VTI. |
| NAT, return paths, and HA | Decide where to apply SNAT when the hub provides Internet egress. On routed private networks, preserve source addresses when required and install return routes to the original prefix. NAT-T carries IPsec over UDP. On pfSense, VTI NAT and `reply-to` depend on a global filtering mode that also affects policy-based tunnels. With CARP, verify the Phase 1 WAN VIP and VTI assignment order on both nodes. |

## Acceptance tests for the firewall pair

1. **Delivery over each tunnel.** With both tunnels negotiated, test A and B independently against the same remote service. Use distinct, comparable monitoring targets reached through each tunnel. Record a complete TCP transaction at the client and destination, the VTI capture, ESP or UDP/4500 on the intended WAN, effective NAT, return traffic, and the MTU under transfer load.
2. **Quality and asymmetry.** First force a new connection from FortiGate into VTI B while pfSense's ordinary route to the source still prefers A. A reply must leave B when the ingress rule's `reply-to` applies. Repeat from the branch and confirm FortiGate sends the reply back through the tunnel the request used. Then add loss or latency only to A. Time the first successful new connection on B and separately track existing sessions. Check PF state, the FortiGate session, both VTI captures, and ESP or UDP/4500 on the two WANs. Experimental steering requires a preferred healthy path to sustain its advantage for 30 seconds before it retakes an eligible incumbent. The reload queue and sample cycle add latency.
3. **Loss of both tunnels.** Keep both physical WANs up with both SAs unavailable. Generate dedicated test traffic for the protected prefix. Capture after NAT on both WANs and check block and destination counters. Acceptance requires zero cleartext delivery of the protected flow, including during reload. Record dropped capture packets.
4. **Recovery and rollback.** Repeat with IKE and ESP rekeys, loss of the active CARP node, and its return. Record the first successful response, the MASTER node for each VIP, and any session interruption. Unbind the policy, open a new connection, and identify the native route it uses. Attach versions, rules, captures, and timestamps without credentials or keys.
